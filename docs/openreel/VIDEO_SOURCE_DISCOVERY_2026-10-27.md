# Массовый поиск видео и получение исходников для Astel

27 октября 2026. Решение для следующего этапа после работающей локальной озвучки.

Для Astel нужен отдельный модуль поиска и каталога материалов. Он получает тему, собирает кандидатов из нескольких источников, показывает подходящие ролики с превью и получает доступные исходники для монтажа. Рекомендуемый первый состав: vidIQ или YouTube Data API для тематических роликов, Brave Video Search для поиска по разным сайтам, Pexels и Coverr для стоковых вставок, локальная библиотека для повторного использования уже полученного материала. Voicebox и OpenReel сохраняют текущие роли.

## Что пользователь получает

В редакторе появляется действие «Найти материал». Пользователь задаёт тему, язык, период и желаемый формат. Для темы «GTA VI» система различает официальные материалы, обсуждения авторов, игровую запись и реальные кадры Майами. Это разные типы материала; совпадение слов в названии не доказывает, что кадры показывают нужную игру или событие.

Результат поиска — подборка карточек с источником, датой, длительностью, разрешением, доступностью файла и причиной соответствия теме. Пользователь может исключить канал или автора, выбрать несколько роликов, получить исходники и отправить их в проект. Для уже скачанного материала следующий поиск использует локальный индекс.

Два режима используют общую карточку: поиск готовых тематических роликов и подбор отдельных кадров под сценарий. Для готовых роликов важны содержание речи, автор, актуальность и источник. Для вставок важны изображённое действие, место, длительность сцены и возможность вертикального кадрирования.

## Получение видео с платформ

Доступный публичный ролик, технически доступный файл и разрешённый исходник — разные свойства карточки. YouTube Data API предоставляет поиск, а его developer policies запрещают API-клиентам сохранять копии audiovisual content без предварительного письменного разрешения YouTube. Фильтр Creative Commons сам по себе не снимает это ограничение API. Для монтажа предпочтителен исходник от автора, собственный архив или другой разрешённый канал получения файла. [YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies).

`yt-dlp` полезен как отдельный механизм получения поддерживаемых разрешённых источников: batch URL, archive от повторной загрузки, выбор качества и `--download-sections` с FFmpeg. Это не система семантического поиска и не источник прав на материалы. Отрезки не гарантируют одинаковую экономию трафика для всех сайтов и форматов. [Документация yt-dlp](https://github.com/yt-dlp/yt-dlp).

Для нынешнего YouTube-пути yt-dlp нужен внешний JavaScript runtime и соответствующий EJS component. Официальная инструкция поддерживает Deno и Node, для Node указывает минимум 22. Весь сбор исходников нельзя привязывать к одному extractor, который зависит от изменений сайта. [EJS setup](https://github.com/yt-dlp/yt-dlp/wiki/EJS).

TikTok Research API предназначен для подходящих исследователей с некоммерческой целью; обычный Display API показывает видео авторизованного пользователя. Это не общий официальный коммерческий keyword search всех TikTok. Для первого этапа использовать доступное discovery через vidIQ и веб-поиск, а получение файлов описывать отдельно. [Research API](https://developers.tiktok.com/products/research-api/), [Display API](https://developers.tiktok.com/docs/en/display-api-get-started).

Apify имеет сторонние Actors для поиска и метаданных. Пример creator listing поддерживает search/channel/transcripts и тарифицирует операции отдельно. Их можно испытать как дополнительного провайдера после выбора конкретного Actor; заявленная цена и возможности не подтверждают доступность каждого ролика и не дают права на переиспользование. [Пример Actor](https://apify.com/zeropointstudio/youtube-scraper). Подключать новый платный сервис для первой версии не требуется.

## Поиск внутри большой библиотеки

После скачивания нужен второй поиск — по сценам и произнесённым словам. Предлагаемый локальный старт: FFmpeg для кадров и proxy, имеющийся Whisper bridge для transcript, scene boundaries и SQLite FTS для текста. Поиск по словам в transcript не гарантирует визуального соответствия сцены; визуальные описания или embeddings добавляются отдельным шагом.

TwelveLabs умеет находить фрагменты по действиям, словам, объектам и картинке после upload и indexing. Это облачный индекс выбранных видео, а не готовый поисковик всех сайтов. Использовать его стоит после сравнения на нашей библиотеке и измерения стоимости. [Search workflow](https://docs.twelvelabs.io/docs/guides/search).

Текущая страница тарифов показывает Free с 3 GB cumulative storage, Plus $29/месяц с 50 GB и Pro $99/месяц с 200 GB, с отдельными allowances. В старых руководствах остались legacy лимиты по минутам; не использовать их для нового бюджета. [Актуальные тарифы](https://www.twelvelabs.io/pricing), [пояснение legacy limits](https://docs.twelvelabs.io/docs/concepts/indexes).

## Что уже есть в Astel и ASAP

Ветка Astel `integration/voicebox-local-first`, исходный commit этого аудита `a95d2089cda5c7845ea8f5d3289c3c2ceb309ea9`: Voicebox panel, сохраняемые задания и WAV, импорт на аудиотаймлайн OpenReel, локальные FFmpeg/transcript components. Search providers и единый каталог найденных роликов предстоит реализовать.

В просмотренном ASAP checkout `275bc4c774cf3317c040c8a4db56ab1cd054745c` сценарию передаются `text`, имя bundled `image` и `source`. Production renderer строит storyboard из изображений с озвучкой; Google adapter загружает preview в Drive. Поэтому этот контур не является готовым сборщиком и семантическим монтажёром произвольных интернет-роликов. Сохраняем очередь, ссылки на источники и version/hash receipts; новые source adapters подключаем отдельно.

Read capability check существующего внешнего ASAP MCP сейчас вернул `tunnel_client_not_seen`. Вывод об имеющемся коде основан на локальном checkout; состояние внешней службы не подтверждено. Туннель и production publishing в этом исследовании не менялись.

## Предлагаемая реализация

```text
Тема и формат
  → варианты запросов и выбранные источники
  → метаданные и превью кандидатов
  → удаление повторов и ранжирование
  → выбор доступных исходников
  → локальное получение и каталог
  → transcript и поиск сцен
  → shot list под окончательную озвучку
  → OpenReel → проверка MP4 → существующий Lazy Distribution
```

Интерфейс источника должен разделять `search`, `get_asset`, `acquire` и `get_segments`. Одни провайдеры возвращают только страницу ролика; другие — download rendition. Карточка хранит `provider`, `source_id`, `source_url`, автора, дату, длительность, геометрию, способ получения и условия использования. Полученный файл добавляет hash, local path, metadata и связь с найденными сценами. Signed URLs хранить отдельно от публичной ссылки и не выводить в обычные логи.

Масштаб начинается с дешёвого поиска метаданных. Для первого пилота задать верхнюю границу до 100 кандидатов по теме, убрать повторы и отобрать около 10 подходящих исходников. Это критерий пилота, а не обещание числа результатов каждого API. Видеобайты загружать после отбора; анализ всех длинных роликов из выдачи заранее перегрузит сеть и Mac.

RAW сохраняется без изменений. Для редактора готовится proxy и план 9:16, а финальный crop выполняется на копии при сборке. В кадрах с лицами, титрами или интерфейсом игры проверять, что важная область не обрезается. Озвучка задаёт финальные длительности; смена темпа требует пересчёта shot list и субтитров.

На текущем Mac тяжёлую локальную индексацию выполнять по очереди с Voicebox. Сетевой поиск, получение метаданных и ограниченное число загрузок могут идти независимо. Новая backend-зависимость от Kevin для первого пилота не нужна.

## Расходы и первый критерий готовности

Brave публикует Search по $5 за 1000 запросов, включая video search, с $5 monthly credits. Например, 100 тем по 10 запросов — 1000 запросов, или $5 по базовой цене до применения credits. Это арифметический пример только поиска, без оплаты исходников, хранения и анализа. [Brave pricing](https://api-dashboard.search.brave.com/documentation/pricing).

Для Pexels и Coverr нужны собственные API keys; право доступа и условия bulk-интеграции проверяются у конкретного аккаунта. Встроенный vidIQ использует credits по вызовам. Покупка подписки или запуск платного batch в этот аудит не входят.

Первый acceptance test: одна тема и несколько вариантов запросов → одна подборка без повторов → 10 доступных файлов с происхождением → импорт в OpenReel → черновик 30–60 секунд с собственным голосом. Измерить отдельно качество поиска, время получения файлов, корректность привязки сцен и совпадение с озвучкой. Подтвердить, что одно повторное действие не скачивает всё заново, а ошибка одного провайдера сохраняет остальные результаты. Автопубликацию не включать в этот тест.

Исследование завершено по текущим документам, public repository history и выбранным участкам кода. Новые API adapters, массовое получение реальных файлов и их совместимость с аккаунтами требуют отдельного implementation pilot; готовой интеграцией этот отчёт их не объявляет.
